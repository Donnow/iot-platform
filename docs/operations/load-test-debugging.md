本文记录 2026-08-03 完成 1000 台设备压测的全过程：从"延迟 7 秒"的误判，
到测量工具自身的 bug，再到数据静默丢失的根因锁定与修复。结论之外，
更重要的是沉淀可复用的排障方法论——这是"讲一个你解决过的难题"的完整剧本。

---

## 1. 整体思路：压测方法论

### 1.1 目标

SRS 定义的验收基线：1000 台设备在线、5000 msg/s、遥测写入 P99 < 100ms。
压测前仓库里只有命令和记录模板，没有任何实测数字。本次压测目标：
跑出真实数字，并对达不到的指标给出**有证据的**解释。

### 1.2 三条原则

**原则一：三方差分定位丢数据环节。**

数据链路是 设备 → EMQX → 平台 → TDengine。链路每一环都有独立的计数器：

| 环节 | 计数器 | 来源 |
| --- | --- | --- |
| 设备发布 | `messages.received` | EMQX nodes metrics |
| 平台消费 | `iot_platform_mqtt_messages_total` | 平台 /metrics |
| 存储落库 | `SELECT count(*)` | TDengine REST |

三处计数互相独立，做 10 秒窗口差分，**差值出现在哪一环，问题就在哪一环**。
这是本次排障最高效的一步：10 秒内把"丢数据"从"平台怀疑"缩小到"存储层"。

**原则二：对照实验分离变量。**

- 无流量基线（0 台） vs 满载（1000 台）：分离"基础链路延迟"与"负载下的积压"
- 1 台 vs 10 台 vs 1000 台：分离"并发相关"与"并发无关"
- 模拟器只改一个变量（tick 相位），其余不动

**原则三：测量工具先行验证。**

平台没有内置端到端延迟指标，先写 `cmd/latencyprobe` 探针：
哨兵设备发布一条遥测 → 轮询平台查询 API 直到数据可见，测得
"发布 → EMQX → 平台消费 → 物模型校验 → TDengine 落库 → 查询可见"的
端到端延迟。**探针用 payload ts 与查询返回时间戳比对，不依赖时钟同步。**

## 2. 探索过程：时间线

### 阶段 1：初测 1000 台，探针显示"延迟 7 秒"

- **操作**：启动 1000 台模拟器，跑探针
- **现象**：样本 2/3 显示 7.2s / 6.9s 延迟
- **误判**：以为是平台处理瓶颈（单线程消费 + 逐条写库，听起来合理）
- **转折**：同时发现平台 mqtt 计数在涨（200 msg/s）、CPU 仅 5%、日志无错误——
  与"处理不过来"矛盾，结论存疑，没有急着"修复平台"

### 阶段 2：无流量测试全 TIMEOUT —— 发现探针自身 bug

- **操作**：停掉所有模拟器，单独跑探针（这是对照实验的"无流量基线"）
- **现象**：5/5 样本全部 TIMEOUT（10 秒内查不到自己发的数据）
- **排查**：数据其实落库了（TDengine 直查可见）——平台链路正常，**探针判定逻辑有 bug**
- **根因**：探针发布 `ts = t0.UnixMilli()`（毫秒截断），判定可见性时用纳秒精度的
  `t0` 比较——`ts` 永远严格早于 `t0`，自己发的消息永远"不可见"
- **连带发现**：阶段 1 的"7 秒延迟"是假象——那两条"成功"样本匹配到的是
  **模拟器**发的消息（同一设备、恰好落在查询窗口内），不是探针自己的消息
- **修复**：比较基准截断到毫秒（`t0.Truncate(time.Millisecond)`）
- **教训**：**先验证测量工具，再相信测量结果**。工具 bug 会把 7 秒假延迟
  变成对平台的错误定罪

### 阶段 3：修复探针后重测 —— 真实延迟其实很健康

- 无流量基线：P50 13ms / P99 26ms
- 1000 台满载：P50 11ms / P95 18ms / P99 18ms / max 25ms（20 样本，2 条超时）
- 结论：**端到端延迟达标（P99 < 100ms）**，之前的"平台瓶颈"假设被推翻

### 阶段 4：三方差分 —— 数据在存储层消失

- **操作**：10 秒窗口同时取 EMQX received / 平台计数 / TDengine count
- **现象**（10 台设备验证）：EMQX +200 | 平台 +190 | TDengine **+71**
- **结论**：设备都发了、平台基本都收到了，**落库只到 35%**——问题在存储层
- **排除**：平台零错误（`mqtt_errors_total` 无新增）、零断线（日志）、
  ACL 全允许（EMQX authorization.deny=0）——不是处理失败，是**静默丢失**

### 阶段 5：1 台 vs 10 台 —— 问题与并发数量相关

- 1 台设备（interval 2s，40 秒）：EMQX +20 | 平台 +19 | TD +20 —— **三方一致，100% 落库**
- 10 台设备（同参数）：落库率掉到 35%
- 结论：基础链路正常，**多设备同时上报时数据互相覆盖**

### 阶段 6：查 TDengine 落库的 ts 分布 —— 铁证

- **操作**：`SELECT ts FROM telemetry WHERE ts > now-130s`，看落库行的时间戳分布
- **铁证**：10 台设备每 2 秒一次上报，落库的 ts 只集中在 **4 个不同毫秒**
  （.323 / .324 / .332 / .333）——其余 6 台的同毫秒数据被覆盖
- **根因链**：
  1. 模拟器所有设备 `time.NewTicker` **同时启动、相位完全同步**，
     同一时刻 tick → payload `ts` 相同（毫秒精度）
  2. TDengine 表主键是 `ts` 单列（SRS 规划的超级表/每设备子表在实现时
     退化成单表），**同 ts 的 INSERT 静默覆盖旧行，不报错**
  3. 平台对覆盖无感知：计数正常、无错误、无日志 —— "看起来一切正常"

### 阶段 7：修复与验证

- 修复模拟器：连接后对 ticker 施加 **0–1000ms 随机相位偏移**，让设备
  上报时间戳自然散布（真实设备的时间戳天然分散，同步 tick 本就是不真实的负载模式）
- 验证：10 台落库率 **35% → 95%**；ts 分布从 4 个毫秒变成每台独立毫秒
- 正式压测（1000 台）：落库率 ~75%（剩余同毫秒碰撞概率所致，见下）

## 3. 找到的 Bug（按层次）

### Bug 1（测量工具层）：latencyprobe 时间比较精度

| 项 | 内容 |
| --- | --- |
| 现象 | 探针自己发的消息永远 TIMEOUT，且"成功"样本匹配到别人的数据 |
| 根因 | 发布 `ts = t0.UnixMilli()`（毫秒），判定用 `!ts.Before(t0)`（纳秒），恒为 false |
| 修复 | 比较基准 `t0.Truncate(time.Millisecond)` |
| 性质 | 工具正确性 bug，不是产品 bug，但会污染一切下游结论 |

### Bug 2（模拟器层）：tick 相位同步导致 ts 相同

| 项 | 内容 |
| --- | --- |
| 现象 | 多设备落库率骤降（10 台 35%、1000 台 ~17%），平台零感知 |
| 根因 | 所有设备同刻启动 `time.NewTicker`，同一毫秒发布，payload ts 相同 |
| 修复 | `internal/devicesim/device.go`：连接后随机相位偏移 0–1000ms |
| 验证 | 10 台落库率 35% → 95%，ts 逐设备散布 |
| 性质 | 模拟器不真实（同步 tick 是人为制造的主键碰撞），真实设备时间戳天然分散 |

### 架构偏差（存储层）：TDengine 单表 ts 主键 vs SRS 超级表设计

| 项 | 内容 |
| --- | --- |
| 现状 | `CREATE TABLE telemetry (ts TIMESTAMP, device_id BINARY(128), ...)` 单表，ts 为唯一主键 |
| 问题 | 同毫秒多设备上报相互覆盖（静默），真实场景概率低但存在（同机房设备 NTP 同步后同毫秒上报并不罕见） |
| 设计目标 | SRS 规划的超级表 + 每设备子表：子表 ts 主键独立，不同设备互不影响 |
| 处置 | 列为遗留优化（见 issues-encountered.md 遗留观察项）；改动涉及存储层 SQL 与查询语义，需配套测试 |
| 教训 | **"零错误"不等于"没丢数据"**：存储层静默合并是这类问题最隐蔽的形态 |

## 4. 修复思路

### 4.1 修复顺序：工具 → 生成 → 存储

1. **先修测量工具**（latencyprobe）：测量不可信，后面一切判断都不可信
2. **再修模拟器**（tick 相位）：让"生成"贴近真实设备，问题从源头消失
3. **存储层列为后续**：单表改超级表工作量大（SQL + 查询语义 + 测试），
   且在当前场景（时间戳已散布）下剩余碰撞率 ~25% 为概率性、可量化、
   可解释——先记录，不阻塞压测结论

### 4.2 为什么修模拟器而不是平台

压测的职责是**暴露**问题而不是**掩盖**问题。三方差分证明平台消费、校验、
写入全部正常（零错误），丢数据发生在"同 ts 覆盖"——这是模拟器制造了
**现实中不存在的负载模式**（同步 tick）撞上了存储层的主键设计。
修模拟器让负载变真实；存储层的超级表改造是独立的架构债，单列跟踪。

### 4.3 残留问题与演进路线

| 问题 | 影响 | 路线 |
| --- | --- | --- |
| TDengine 单表 ts 主键 | 同毫秒多设备覆盖（当前 ~25% 概率性） | 超级表/每设备子表 |
| 平台消费单线程（paho 回调 + 逐条 PG 查询 + 逐条 TDengine HTTP 写入） | 200 msg/s 已接近上限，5000 msg/s 目标无法达成 | 消费端多 worker、产品查询缓存、TDengine 批量写入（或 Kafka 削峰） |
| 1000 台同时连接时认证回调瞬时超时（启动风暴） | 启动瞬间 ~10 台连接失败，退避重连后恢复 | 模拟器连接分批、平台认证缓存 |

## 5. 方法论沉淀（面试可讲）

1. **差分定位法**：数据链路每一环都有独立计数器，同步差分，
   差值在哪一环问题就在哪一环——比猜日志快一个数量级
2. **对照实验**：无流量基线分离"基础延迟"与"负载效应"；1/10/1000 台
   梯度定位"并发相关"问题
3. **先验证测量工具**：工具的 bug 会把假现象变成对系统的错误定罪
   （本例：7 秒假延迟差点被归咎于平台架构）
4. **"零错误 ≠ 没丢数据"**：存储层静默合并/覆盖是最隐蔽的数据丢失形态，
   压测要核对**两端的数字**（入口计数 vs 落库计数），不能只看错误日志
5. **模拟器要模拟现实**：同步 tick、固定间隔、固定 payload 都是不真实的
   负载模式，会撞出真实场景不存在（或概率极低）的问题
6. **不掩盖问题的修复顺序**：先让工具可信、再让负载真实、最后评估
   架构债——每一步都有验证数字（35% → 95%）而不是"应该修好了"
