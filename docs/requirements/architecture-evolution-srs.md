## 1. 文档目的

当前平台已经完成设备接入、遥测、规则告警、设备影子、指令和 OTA 的完整链路，
并在单机 Compose 环境验证了 1000 台设备、200 msg/s 的稳定运行。本阶段不重写现有
系统，也不默认拆分微服务，而是在保持可运行性和开发效率的前提下，补齐生产环境所需
的可靠性、安全边界、可观测性和可演进能力。

本文描述系统在架构演进阶段**必须具备什么能力**。具体组件选型、表结构细节和代码
拆分方式在对应设计文档或 ADR 中确定。

## 2. 当前基线与问题范围

### 2.1 已有能力

| 领域 | 当前能力 |
| --- | --- |
| 部署 | Go 分层单体 + EMQX + PostgreSQL + Redis + TDengine + Vue，Compose 一键启动 |
| 接入 | 一机一密、设备级 topic ACL、共享订阅、断线重订阅 |
| 遥测 | 物模型校验、按设备分片 worker、产品缓存、TDengine 批量写与内存重试 |
| 业务 | 规则告警、影子同步、指令状态、OTA 进度 |
| 验证 | 单元测试、进程内集成测试、CI 构建、1000 台设备压测 |

### 2.2 需要解决的问题

| 问题 | 当前影响 | 本阶段目标 |
| --- | --- | --- |
| 接入队列与失败批次仅在内存中 | 进程退出或队列满时可能丢失消息 | 已确认消息可恢复、可重放、可审计 |
| 数据库状态与 MQTT 发布分两步 | 崩溃时可能出现状态已提交但消息未发送 | 使用可靠事件边界保证最终一致 |
| Redis 名义为缓存但错误会中断业务 | 缓存故障扩大为业务故障 | 权威存储可用时核心业务继续服务 |
| 内部回调与浏览器 MQTT 凭据边界较弱 | 存在伪造生命周期或扩大订阅权限的风险 | 内部接口隔离、浏览器使用用户级授权 |
| HTTP/MQTT 层直接编排业务 | 文件持续膨胀，故障路径难以独立测试 | 协议适配与业务用例分离 |
| 健康检查与指标粒度不足 | 服务“进程在线但功能不可用”时难发现 | 可判定存活、就绪、积压和端到端延迟 |
| 多实例状态与消息顺序未定义 | 直接水平扩容会破坏规则窗口语义 | 扩容前明确运行角色、分区和状态归属 |

## 3. 演进原则与约束

1. 保持模块化单体作为默认部署形态；只有独立扩缩容或故障隔离产生实际收益时才拆分运行角色。
2. PostgreSQL 继续作为产品、设备、规则、告警、指令、影子和 OTA 元数据的权威存储。
3. Redis 默认承担缓存和短期状态职责；若用于持久化流，必须使用独立容量、持久化和淘汰策略。
4. TDengine 继续作为遥测查询的权威存储，所有重试和重放必须具备幂等语义。
5. API 和 MQTT topic 尽量向后兼容；破坏性变更必须提供迁移窗口和版本说明。
6. 不以“技术先进”为理由引入 Kafka、CQRS、事件溯源或完整微服务体系；引入基础设施必须有测量数据和业务需求支持。
7. 每项功能必须同时定义正常路径、依赖故障路径、进程重启路径和可观测信号。

## 4. 角色与使用场景

| 角色 | 新增或强化的使用场景 |
| --- | --- |
| 平台管理员 | 管理规则和产品生命周期、轮换设备密钥、查看死信并执行重放 |
| 运维人员 | 查看就绪状态、积压、发布失败、缓存降级和端到端链路指标 |
| 设备 | 在重复投递、平台重启和凭据轮换期间保持协议兼容 |
| EMQX | 通过受保护的内部通道完成认证、ACL 和生命周期回调 |
| 管理台 | 通过用户 JWT 订阅有权限的实时事件，不持有平台级 Broker 凭据 |
| 发布/消费工作进程 | 可恢复处理持久化接入消息和 outbox 事件，并隔离毒消息 |

## 5. 功能需求

### 5.1 可靠性与一致性

**FR-REL-01 Redis 缓存故障降级**  
当 Redis 连接失败、超时或返回非预期数据时，设备影子读取必须回退到 PostgreSQL；
影子或设备状态的 PostgreSQL 写入成功后，缓存回写失败不得把已经成功的业务操作报告为
失败。系统必须记录缓存错误、降级次数和恢复时间。  
验收：停止 Redis 后，影子 GET/PUT 仍按 PostgreSQL 权威数据工作；恢复 Redis 后首次读取
能够重新回填；响应和日志不存在“数据库已提交但 API 报业务失败”的歧义。

在线状态属于短期状态。Redis 不可用且平台无法确定实时状态时，API 必须返回明确的
`unknown` 或降级标记，不得把历史 PostgreSQL 状态伪装成实时在线状态。

**FR-REL-02 遥测持久化接入**  
平台只有在消息进入可恢复边界后，才能把它视为已经接受。MQTT 回调、内部队列或下游
TDengine 暂时不可用时，已接受消息必须在进程重启后继续处理。重复投递必须按稳定消息键
幂等处理。  
验收：在接收后、TDengine 写入前强制终止平台，重启后消息最终可查；连续投递相同消息
不会产生重复告警、重复命令或不可解释的遥测行；容量耗尽时平台产生明确告警和背压，
不得只记录一条 warning 后静默丢弃。

**FR-REL-03 下行事件最终一致**  
创建命令、更新影子 desired、创建 OTA 任务和规则触发命令时，业务状态与待发布事件必须
原子提交。后台发布器负责发布、确认、退避重试和状态更新。  
验收：在事务提交后、MQTT 发布前终止平台，重启后事件仍能发布；MQTT 暂时不可用时 API
返回可追踪的 accepted/pending 状态，而不是丢失任务；事件最终成功、失败或进入死信均可查询。

**FR-REL-04 毒消息隔离与重放**  
校验失败、超过最大重试次数或下游长期拒绝的消息必须进入死信区，保存原始 topic、payload、
接收时间、错误原因、尝试次数和关联业务键。管理员可查询、过滤、重放或确认丢弃。  
验收：一条毒消息不会阻塞同分区后续消息；重放操作有管理员鉴权和审计；重复点击重放
不会产生重复业务副作用。

**FR-REL-05 幂等业务动作**  
命令、告警、影子更新、OTA 进度和 outbox 发布必须定义稳定幂等键。系统必须区分“重复请求”
与“新的业务动作”。  
验收：网络超时后客户端使用同一幂等键重试，返回原业务结果；不同幂等键可以创建新动作；
幂等记录具有明确保留时间。

**FR-REL-06 连接风暴保护**  
平台必须承受设备批量重连，不因 PostgreSQL 查询或生命周期补发的瞬时并发导致大面积认证
超时。模拟器必须支持启动抖动和分批连接，以复现真实恢复场景。  
验收：1000 台设备在规定窗口内重连时最终全部上线；认证错误率、P99 和数据库连接池使用率
被记录；单台失败使用有上限的退避重试，不形成同步重试风暴。

### 5.2 安全边界

**FR-SEC-01 EMQX 内部接口保护**  
认证、ACL 和生命周期回调必须使用独立内部网络边界，并通过共享签名、mTLS 或等价的服务
身份机制认证调用方。内部凭据必须支持轮换，不得写入日志。  
验收：从公开监听地址直接请求内部接口失败；无效签名、过期时间戳和重放请求被拒绝；
EMQX 正常调用不受影响；失败请求产生不包含密码的安全审计记录。

**FR-SEC-02 设备密钥生命周期**  
设备密钥必须由加密安全随机源生成，数据库只保存不能直接用于登录的摘要。系统必须支持
密钥版本、轮换、短期双密钥兼容窗口和立即吊销。高熵设备密钥的摘要方案必须兼顾认证风暴
下的验证成本。  
验收：创建和轮换响应仅展示一次明文；查询接口和日志不返回明文；迁移后现有设备在兼容
窗口内可连接；吊销后旧密钥不能认证。

**FR-SEC-03 管理台实时访问控制**  
管理台实时数据必须通过用户 JWT 鉴权，并按用户角色和资源范围过滤。生产前端产物不得
包含平台级 MQTT 用户名或密码。  
验收：未登录、过期 JWT 和无权限用户无法订阅事件；用户退出登录后实时连接关闭；构建产物
扫描不出现平台 MQTT 密码；实时状态更新延迟不高于 2 秒。

**FR-SEC-04 RBAC 与登录防护**  
系统至少支持 `admin` 和 `operator` 两类角色。管理员可执行产品/规则变更、凭据轮换、死信
重放和用户管理；运维人员可查看数据、处理告警和下发允许的设备指令。登录端点必须具备
按用户名和来源的速率限制，并保持统一失败响应。  
验收：权限矩阵中的禁止操作返回 403；连续失败登录受到限制；不存在通过错误文案枚举用户；
授权决策记录用户名、角色、操作和结果。

### 5.3 应用层与业务完整性

**FR-APP-01 业务用例边界**  
发送命令、更新影子、创建 OTA、处理遥测和设备生命周期等跨仓储操作必须由应用服务统一
编排。HTTP/MQTT 层只负责解析协议、调用用例并映射响应。  
验收：应用服务可在不启动 HTTP 或 MQTT 客户端的情况下测试；同一业务规则不会在多个协议
入口重复实现；repository 接口保持面向业务能力而不是数据库表。

**FR-APP-02 规则读取缓存**  
规则按产品缓存，创建、更新、启停或删除规则后必须主动失效；TTL 只作为兜底。并发缓存未命中
必须合并加载，避免数据库击穿。  
验收：稳态遥测不会每条查询 PostgreSQL；规则变更在 2 秒内生效；缓存故障或失效不影响规则
正确性；命中率、加载延迟和加载错误可观测。

**FR-APP-03 产品与规则完整生命周期**  
系统必须提供产品更新，以及规则更新、启停和删除能力。被设备引用的产品不得直接物理删除；
破坏物模型兼容性的修改必须返回冲突或要求显式迁移。  
验收：接口、OpenAPI、前端和缓存失效行为一致；禁用规则不再产生新动作；所有变更有更新时间
和操作者审计。

**FR-APP-04 告警自动恢复**  
规则条件从匹配恢复为不匹配时，系统应按规则策略自动将对应活动告警标记为 recovered/resolved，
且不得覆盖人工处理备注。  
验收：立即规则和持续时间规则都能正确恢复；抖动场景不会重复创建/恢复同一告警；恢复动作
可配置为自动或仅记录事件。

**FR-APP-05 指令后台超时**  
pending 指令超过配置时限后，后台任务必须主动标记 timeout，而不是等待查询接口触发。任务
需要支持多实例并发安全和可重复执行。  
验收：不调用查询接口也能在时限后看到 timeout；迟到回复按明确策略处理并记录；后台扫描延迟
和处理数量有指标。

**FR-APP-06 实时遥测快照**  
成功接受的最新属性值必须维护为设备快照。Redis 命中时直接返回；未命中时从 TDengine 回源并
回填；Redis 故障遵守 `FR-REL-01`。  
验收：1000 台设备负载下快照接口 P99 小于 50ms；不同属性最后更新时间分别保留；乱序消息
不得覆盖时间更新的快照。

**FR-APP-07 OTA 进度定向关联**  
OTA 进度消息必须携带或推导出稳定任务标识，平台不得扫描产品下全部任务和目标设备数组来
定位更新对象。  
验收：单条进度更新使用有索引的定向查询；未知任务或非目标设备返回可观测错误；重复进度上报
幂等；阶段不可非法倒退。

**FR-APP-08 影子版本控制**  
设备影子必须包含单调递增 `version`。管理端更新可携带 `expected_version`；版本不匹配时返回
409，且不得覆盖较新数据。设备上报 reported 和平台下发 desired 都必须携带 version。  
验收：两个客户端并发更新时只有符合版本条件的请求成功；重连补发不会应用旧版本；未携带
expected_version 的旧客户端在兼容期内按文档策略工作。

### 5.4 运行、迁移与发布

**FR-OPS-01 存活和就绪探针**  
系统提供 `/livez` 和 `/readyz`。`/livez` 只反映进程是否能够继续运行，不因外部依赖短暂故障
失败；`/readyz` 反映 PostgreSQL、MQTT 连接与订阅、遥测写入通道以及当前模式所需依赖。  
验收：MQTT 未订阅或关键队列不可服务时 ready 返回 503 和结构化原因；依赖恢复后自动恢复 200；
Compose/Kubernetes 使用 ready 状态接收流量，不能形成重启抖动。

**FR-OPS-02 运行指标与告警**  
平台必须提供 HTTP 请求量、状态码和延迟分布；MQTT 接收/处理/丢弃、分片队列深度；批写大小
和延迟；pending/dead-letter 数量；outbox 发布延迟；缓存降级；规则缓存命中率；登录限制等指标。  
验收：所有指标符合 Prometheus 格式并有 HELP/TYPE；运维文档给出 dropped、积压、就绪失败、
发布延迟和认证错误的建议告警阈值。

**FR-OPS-03 链路关联标识**  
HTTP 请求使用 `request_id`，MQTT 消息使用 `message_id`，日志必须同时携带可用的 device_id、
command_id、task_id 或 outbox_id。跨 goroutine 和重试时关联标识不得丢失。  
验收：从一次命令 API 请求能够检索到数据库提交、outbox 发布和设备回复的完整日志链；敏感
payload 和凭据不进入日志。

**FR-OPS-04 版本化 schema 迁移**  
PostgreSQL 与 TDengine 结构变更必须通过有序、可重复、可查询的迁移执行。应用启动不得临时
创建零散业务表来掩盖缺失迁移。  
验收：空库和旧版本库执行相同迁移后结构一致；重复执行无副作用；迁移失败阻止新版本就绪；
每次迁移包含兼容性、数据回填和回滚说明。

**FR-OPS-05 API 契约单一事实来源**  
仓库只能维护一份手写 OpenAPI 源文件，运行时嵌入文件和其他副本由构建生成。CI 必须检查生成
结果和实现所需路由的一致性。  
验收：修改一处契约即可更新 Swagger UI 与仓库文档；生成结果存在差异时 CI 失败；需求、API、
README 和运行手册中的能力描述完成一次一致性审计。

**FR-OPS-06 完整 Compose E2E**  
CI 必须提供手动或定时的 L3 作业，启动真实 EMQX、PostgreSQL、Redis、TDengine、平台和前端，
执行设备注册、认证、遥测、影子、命令、规则告警和 OTA 主链路。  
验收：测试不使用 memory store 替代真实依赖；失败时保存容器日志、指标和测试输入；同一脚本
可在开发机复现。

**FR-OPS-07 可追踪镜像发布**  
版本 tag 可生成平台和前端镜像并推送到镜像仓库。镜像必须标记版本、Git SHA 和构建时间，生成
SBOM 并执行基础漏洞扫描。  
验收：只有测试、构建和 E2E 通过的版本可发布；部署者可由镜像标签追溯到源码提交；失败发布
不会覆盖稳定标签。

### 5.5 前端可维护性

**FR-FE-01 按业务域拆分**  
前端应拆分 overview、devices、alarms、rules、products 和 ota 视图，以及 API、实时连接、图表和
表单逻辑。应用入口只保留导航、全局认证和布局。  
验收：每个业务域能独立加载和测试；拆分不改变现有交互；不因拆分强制引入当前不需要的全局
状态框架。

**FR-FE-02 实时通道统一管理**  
实时连接必须集中处理连接、重连、鉴权刷新、订阅范围、错误和清理。组件不得各自创建长期连接。  
验收：页面切换不会泄漏连接或重复订阅；登录状态变化能正确重建/关闭连接；降级到手动刷新时
界面有明确状态。

**FR-FE-03 前端行为测试**  
除 API helper 外，必须覆盖登录、设备选择、命令轮询、影子版本冲突、实时事件更新和关键表单。  
验收：测试能够发现权限失效、定时器未清理、重复订阅和错误响应未展示等回归；CI 同时运行测试
和生产构建。

**FR-FE-04 前端加载预算**  
管理台必须按业务视图和重型依赖拆分生产 bundle，ECharts、实时通信库和非首屏视图应按需加载。
CI 必须记录构建产物大小并执行稳定的 bundle budget。  
验收：生产构建不再产生 500 kB chunk 警告；首屏不下载未进入视图所需的业务代码；超过预算时
CI 失败并输出增长最大的产物。

### 5.6 扩容与容量治理

**FR-SCALE-01 可配置运行角色**  
同一代码库和镜像应支持 `all`、`api`、`ingestion` 三种运行角色，使 HTTP 与 MQTT 消费能够独立
扩缩容，同时保留 Compose 默认一体化运行体验。  
验收：每种角色只初始化需要的依赖；配置错误启动失败并给出原因；单体模式行为与当前兼容。

**FR-SCALE-02 多实例保序与规则状态**  
在启用多个 ingestion 实例前，必须定义同设备消息的分区规则、故障转移和规则持续时间状态归属。
若规则状态允许重启重置，必须明确业务影响；若不允许，状态必须外置并支持原子更新。  
验收：多实例故障转移测试中，同设备命令回复、影子和 OTA 进度不会因乱序产生非法状态；持续
时间规则不会重复触发。

**FR-SCALE-03 消息基础设施决策门槛**  
只有出现以下至少一项需求时才进入 Kafka 或等价组件设计：当前持久化流水线无法满足已验证 SLO；
多个独立消费者需要各自回放；需要跨实例长周期保留；需要按分区水平扩容。  
验收：ADR 包含当前方案、WAL、Redis Streams 和 Kafka 的吞吐、恢复语义、运维成本与回滚对比；
先完成当前架构 5000 msg/s 基准，再根据证据决策。

**FR-SCALE-04 遥测生命周期管理**  
在明确数据保留和成本需求后，平台应支持热数据保留、归档、删除与历史查询。归档不得阻塞实时
写入，删除必须可审计。  
验收：保留策略按产品配置；归档和恢复有容量及耗时记录；历史查询明确数据所在层和最大响应时间。

## 6. 非功能需求

### 6.1 可靠性

| ID | 指标 | 要求 |
| --- | --- | --- |
| NFR-REL-01 | 已接受消息恢复 | 进程非正常退出后可重放，不能因内存队列丢失 |
| NFR-REL-02 | 缓存降级 | PostgreSQL 可用时，单独 Redis 故障不阻断影子核心读写 |
| NFR-REL-03 | outbox 最终交付 | MQTT 恢复后 60 秒内恢复发布积压，失败可追踪 |
| NFR-REL-04 | 幂等 | 相同消息或幂等键重复处理不产生重复业务动作 |
| NFR-REL-05 | 优雅关闭 | 停止接收后排空或持久化在途消息，超时后明确记录未完成数量 |

### 6.2 性能

| ID | 指标 | 当前阶段要求 |
| --- | --- | --- |
| NFR-PERF-01 | 基线负载 | 1000 台设备、200 msg/s 下性能不低于现有实测 |
| NFR-PERF-02 | 规则查询 | 稳态 PostgreSQL 规则查询量不随每条遥测线性增长 |
| NFR-PERF-03 | 快照接口 | 1000 台负载下 P99 < 50ms |
| NFR-PERF-04 | 连接风暴 | 1000 台设备在 60 秒窗口重连，最终连接成功率 100% |
| NFR-PERF-05 | 扩容门槛 | 在引入 Kafka 前验证当前架构 5000 msg/s 的吞吐、P99 和资源消耗 |

每次性能结论必须记录硬件、镜像版本、消息大小、设备数、持续时间、P50/P95/P99、错误数、
入口计数、持久化计数以及 CPU/内存/网络使用量。

### 6.3 安全

| ID | 要求 |
| --- | --- |
| NFR-SEC-01 | 内部接口默认拒绝公网访问，服务身份验证失败时 fail-closed |
| NFR-SEC-02 | 设备密钥、管理员密码、JWT 密钥和内部签名密钥不以明文写入日志或查询响应 |
| NFR-SEC-03 | 所有管理写操作执行 RBAC，敏感操作记录审计 |
| NFR-SEC-04 | 凭据支持轮换，轮换过程不中断所有设备且有明确兼容窗口 |

### 6.4 可观测性与可维护性

| ID | 要求 |
| --- | --- |
| NFR-OBS-01 | 从接入到落库或从 API 到设备回复的关键阶段均有指标和关联日志 |
| NFR-OBS-02 | 指标标签必须有界，禁止把 device_id、command_id 等高基数字段作为 Prometheus 标签 |
| NFR-MAINT-01 | 需求、API、代码、迁移和测试之间存在稳定编号与可追踪关系 |
| NFR-MAINT-02 | 新增应用用例必须包含成功、依赖失败、重试/幂等和权限测试 |

## 7. 逻辑数据模型

以下模型定义必须保存的信息，不限制最终数据库或消息中间件实现。

### 7.1 持久化接入记录

| 字段 | 说明 |
| --- | --- |
| message_id | 稳定唯一消息标识/幂等键 |
| topic、device_id、product_key | 路由和业务归属 |
| payload | 原始消息或可验证的规范化内容 |
| received_at | 平台接收时间 |
| status | pending/processing/succeeded/dead |
| attempts、next_attempt_at | 重试控制 |
| last_error | 最后一次失败摘要，不含敏感信息 |

### 7.2 Outbox 事件

| 字段 | 说明 |
| --- | --- |
| event_id | 唯一发布和幂等标识 |
| aggregate_type、aggregate_id | command/shadow/ota/rule_action 及业务 ID |
| event_type、topic、qos、retained | 发布契约 |
| payload | 下行消息内容 |
| status | pending/publishing/published/dead |
| attempts、next_attempt_at | 重试控制 |
| created_at、published_at | 延迟与审计 |
| last_error | 最后一次失败摘要 |

### 7.3 设备凭据

| 字段 | 说明 |
| --- | --- |
| device_id | 设备标识 |
| secret_digest | 不可直接登录的摘要 |
| key_version | 凭据版本 |
| active_from、expires_at | 有效窗口 |
| revoked_at | 吊销时间 |
| rotated_at | 轮换时间 |

### 7.4 影子并发字段

设备影子增加 `version`，每次 desired/reported 成功更新后原子递增。更新条件必须能够表达
`WHERE version = expected_version`，冲突不得通过最后写入覆盖来隐藏。

## 8. 接口需求

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/livez` | 公开 | 进程存活，不执行重型依赖探测 |
| GET | `/readyz` | 公开/内网 | 返回整体就绪和各组件状态 |
| GET | `/api/events` | 已登录 | SSE/WebSocket 握手，按权限订阅实时事件 |
| POST | `/api/devices/:id/credentials/rotate` | admin | 轮换设备密钥，仅返回一次新密钥 |
| PATCH | `/api/products/:product_key` | admin | 更新产品兼容字段 |
| PATCH | `/api/rules/:id` | admin | 更新或启停规则 |
| DELETE | `/api/rules/:id` | admin | 删除/归档规则 |
| GET | `/api/operations/dead-letters` | admin | 查询死信 |
| POST | `/api/operations/dead-letters/:id/replay` | admin | 幂等重放死信 |

现有命令、影子和 OTA 写接口应支持 `Idempotency-Key`。影子更新请求应支持
`expected_version`，冲突统一返回 HTTP 409。所有新增接口必须同步 OpenAPI 与后端测试计划。
